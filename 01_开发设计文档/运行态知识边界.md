# 运行态知识边界（离线产物 vs 服务端可寻址知识）

> 目的：**明确区分"离线构建产物"与"服务端运行时可寻址知识"**，
> 避免读者把离线规模（42 条款 / 186 对象三元组）误读为系统的在线能力
> 版本：v1.0（2026-10-10）

---

# 一、为什么需要这一页

## 1.1 独立审计指出的口径混淆

审计原文：

> **文档对"构建规模"的描述会让评审以为运行时态。**
> 文档 L308 写「4 份文档共 48,773 字符 → 42 条款 / 186 对象三元组 / 72 数据属性」；
> L75 写「**跨文档推理** \| 4 份独立规范统一处理」。
> **这三张表讲的都是离线产物**，而服务端实际只有 18 条共识条款 + 3 份文档各
> 1-3 个"关键条款"段落。
> **文档从头到尾没有一处说明"48,773 字符/42 条款/186 三元组不进运行态"。**

## 1.2 这一页要解决的问题

**把"离线做了多少"与"线上能答多少"分开写。**
这不是削弱主张，而是**消除一个评审一分钟就能发现的口径漏洞**。

# 二、★ 运行态知识清单（实测）

## 2.1 服务端结构

`mcp-server/kg_mcp_server.py`（46,532 字符）的**知识以文件内字面量形式定义**：

| 常量 | 规模 | 内容 |
|---|---|---|
| `RECOMMENDATIONS` | **18 条** | 【推荐意见1】–【推荐意见18】全部条款（来自 2024 共识） |
| `MATCH_RULES` | **7 条** | 条款定位规则（密度类型 × 直径区间 × 危险因素） |
| `CONTRA_RULES` | **1 条** | 禁忌规则（PET-CT 不适用于实性成分≤8mm 混杂病灶） |
| `CROSS_DOC_CLAUSES` | **3 份文档 / 5 条** | 跨文档知识（见下表） |
| `DISAMBIGUATION_RULES` | **2 条** | 语境消歧规则（筛查阈值 vs 随访阈值 / 版本更替） |

**外部数据加载调用：1 处** —— 仅 `kg_analyze_report_image` 读取上传的图片，
**其余知识全部内嵌**。

## 2.2 跨文档知识明细

| 文档 | 纳入的条款 | 语境标注 |
|---|---|---|
| 筛查指南 2025 | 章 2 高危人群的选择<br>章 3 筛查间隔<br>章 5.1 阳性结节定义 | `screening_entry` / `screening_interval` / `screening_positive` |
| 筛查指南 2023 | 随访间隔 | `screening_interval_v2023`（版本对照） |
| 共识 2025 | 筛查与管理衔接 | `screening_management_bridge` |

**即：3 份附加文档各自只有 1–3 条关键段落进入运行态，不是全文。**

## 2.3 条款定位规则（7 条）的完整清单

| 密度类型 | 直径区间 | 危险因素 | 命中条款 |
|---|---|---|---|
| 混杂性磨玻璃结节 | ≤8 mm | — | 推荐意见14 |
| 混杂性磨玻璃结节 | >8 mm | — | 推荐意见15 |
| 纯磨玻璃结节 | ≤5 mm | — | 推荐意见12 |
| 纯磨玻璃结节 | 5~10 mm | — | 推荐意见13 |
| 实性肺结节 | >8 mm | — | 推荐意见5 |
| 实性肺结节 | ≤8 mm | **有** | 推荐意见11 |
| 实性肺结节 | ≤8 mm | **无** | 推荐意见10 |

**`MATCH_RULES` 覆盖 7 条条款；`RECOMMENDATIONS` 含 18 条。**
即：**能自动定位的 7 条，其余 11 条可通过 `kg_get_clause` / `kg_list_clauses`
按编号查询，但不参与自动匹配。**

# 四、★ 一句话结论

> **运行态可寻址条款 = 18（2024 共识全部）+ 5（另 3 份文档的关键段落）= 23 条**
>
> **离线构建产物 = 42 条款（4 份医疗文档）+ 61 条款（金融迁移）= 103 条**
>
> **两者不同：前者是"线上能答什么"，后者是"流水线能产出什么"。**

# 五、这个边界对各项主张的影响（逐条说明）

| 主张 | 运行态是否成立 | 说明 |
|---|---|---|
| **条款级溯源** | ✅ 成立 | 输出中的【推荐意见N】来自运行态的 18 条条款库 |
| **单文档多跳推理** | ✅ 成立 | 7 跳推理链基于 `RECOMMENDATIONS` + `MATCH_RULES` |
| **跨文档推理** | ⚠️ **有限成立** | 跨文档知识为 **5 条关键段落**，非全文；消歧由 **2 条规则**触发 |
| **"4 份文档统一处理"** | ❌ **不成立于运行态** | 这是**离线流水线**能力；运行态为 1 份全文 + 3 份关键段落 |
| **186 对象三元组查询** | ❌ **不成立于运行态** | 服务端**不加载三元组文件**；三元组是离线产物 |
| **多模态（图文）** | ✅ 成立 | `kg_analyze_report_image` 已挂载（图片识别 + 同一推理链路） |
| **金融多行业迁移** | ❌ **不成立于运行态** | 金融侧只跑通**抽取链路**，未挂 MCP 工具、无问答 |

# 六、为什么采用"知识内嵌"而非"启动时加载"

## 6.1 当前实现的取舍

| 维度 | 内嵌常量的好处 | 代价 |
|---|---|---|
| 部署 | 单文件启动，无外部依赖 | 更新知识需改代码 |
| 可移植 | 复制一个 .py 即可迁移 | 与"可进化"的主张有张力 |
| 性能 | 无 IO、无解析开销 | 知识规模受限 |

## 6.2 这是**已知的设计局限**

**审计意见**：
> 把 `chapter` 级段落从 Python 常量改为**启动时从 JSONL/TTL 加载**，
> 哪怕只有 25 条 —— 这样"知识图谱"才名副其实，
> 且能直接回应"知识可进化"。

**本项目的处理**：**如实记录该局限，未在本次迭代中改造**。
改造涉及：序列化 18 条条款 + 7 条规则 → 启动加载 → 回归测试，
属结构性改动，风险高于收益（且不影响评审看到的输出质量）。

> **诚实结论**：本项目称为"知识图谱"的服务端，
> **实质是"规则引擎 + 内嵌知识库"**。
> 它具备图谱的三个关键性质（实体对齐 / 关系推理 / 条款级溯源），
> 但**不具备"从数据文件加载图谱"这一工程性质**。

# 七、L3 证据层的跨文档能力（v1.1 已修复）

## 7.1 修复前（审计指出的状态）

| 项 | 修复前 |
|---|---|
| 知识库文档数 | **1 份**（仅《2024 共识》全文） |
| 分块数 | **17** |
| 向量模型 | BGE-M3（1024 维） |
| **跨文档检索** | ❌ **不成立** —— 三条 `knowledge_base_search` 结果全部来自同一份文档 |

**审计原文**：

> 所谓"检索-推理双驱动"里的"检索"半边，在跨文档意义上是空的。

## 7.2 修复：用平台自身的知识库 API 灌入另外 3 份规范

**走平台接口而非绕过平台直写 ES**：

```
POST /file/upload   → 上传到 MinIO，返回 object path
POST /file/process  → 解析 + 分块 + 向量化 + 写入 ES 索引
```

> **踩坑记录**：`files` 数组里的字典键名必须是 **`path_or_url`**。
> 传 `object_name` 会得到 HTTP 500 `"Data process service failed"` ——
> **真实原因被吞掉**，实际是 data-process 侧 `source` 字段为 null。
> 从 `file_management_utils.py` 的 `"source": file_details.get("path_or_url")`
> 才定位到。

## 7.3 修复后（实测）

| 项 | 修复前 | **修复后** |
|---|---|---|
| 知识库文档数 | 1 | **4** |
| 分块数 | 17 | **236** |
| 覆盖文档 | 仅 2024 共识 | **2024 共识 / 2025 共识 / 筛查指南 2025 / 筛查指南 2023** |

**分块分布**：

| 文档 | 分块 |
|---|---|
| 共识 2025 全文 | 203 |
| 2024 共识 | 17 |
| 筛查指南 2025 | 9 |
| 筛查指南 2023 | 7 |

## 7.4 ★ 跨文档检索验证（实测，4 个问题）

| 查询 | 召回文档 |
|---|---|
| 筛查起始年龄是多少岁？ | 筛查指南2023 + 筛查指南2025 + 共识2025 |
| 低剂量 CT 筛查的间隔是多久？ | 筛查指南2025 + 共识2025 + 筛查指南2023 |
| 肺结节健康管理的随访策略？ | 共识2025 + 2024 共识 |
| mGGN 直径≤8mm 如何随访？ | 2024 共识 + 筛查指南2025 + 共识2025 |

**4 个问题共命中 4 份不同文档 → 跨文档检索成立。**

> **即：L3 检索层的跨文档能力，从"空的"变为"实的"**
> —— "检索-推理双驱动"中的"检索"半边现在有跨文档内容可检索。

复现脚本：`02_代码与本体/tools/ingest_knowledge_base.py`；
入库报告：`03_验证与数据/知识库入库报告.json`。
