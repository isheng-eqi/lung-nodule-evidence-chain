# 一、为什么要有这份核对表

## 1.1 独立审计指出的问题

审计对评测集提出三层同义反复的指控：

| # | 指控 | 证据 |
|---|---|---|
| 1 | 评测对象不是系统，是引擎模块 | `eval_runner.py` 直接 `import kg_mcp_server` 调 `run_inference()` —— **不经 MCP、不经 Nexent、不经 Skill、不过 LLM** |
| 2 | **金标准抄自被测代码** | `build_evalset.py` 的 `GOLD_RULES` 与 `kg_mcp_server.py` 的 `MATCH_RULES` **是同一张表**（连 `d_max: 8`、`has_risk_factor` 分支都逐字对应） |
| 3 | "可溯源率 100%" 是恒真断言 | 取引擎自报的 `traceable` 字段，而该字段在 `NOT_COVERED` 分支**也返回 True** |

**审计定性**："复现的是同义反复，不是能力。"

## 1.2 本轮的修法（只修指控 2）

**把金标准的依据写进数据本身** —— 每条规则记录：
- 共识原文的**章节位置**
- 共识**原文引用**（可直接搜索定位）
- **边界语义说明**（`≤` 与 `>` 的归属）

**第三方复核方法**：打开《肺结节诊治中国专家共识（2024 年版）》全文，
搜索下表 `原文引用` 列的文字，核对区间参数是否与原文一致。
**全程不需要看引擎代码。**

> **诚实说明**：指控 1（评测对象是引擎而非系统）与指控 3（可溯源率恒真）
> **已修** —— 见第五节（该节保留原始指控记录，并标注处理结果）。

# 三、★ 本轮核对中发现的一处真实规则缺陷

## 3.1 问题

`GOLD_RULES` 中实性结节的两条规则：

```python
{"density": "实性肺结节", "d_min": 8, "d_max": 30, "clause": "推荐意见5"}    # 8~30
{"density": "实性肺结节", "d_min": 0, "d_max": 8,  "clause": "推荐意见11"}   # ≤8
```

**在 8.0 mm 处参数重叠。**

## 3.2 与之前修过的问题同类

| 轮次 | 密度类型 | 问题 |
|---|---|---|
| 第 29 轮 | **mGGN** | `(0,8]` 与 `[8,30]` 在 8mm 处重叠 → 已修（改为半开区间） |
| **本轮** | **实性结节** | `[0,8]` 与 `[8,30]` 在 8mm 处重叠 → **同类问题，当时未检查** |

## 3.3 判定：**原文语义不重叠，是我的区间参数写法有歧义**

**共识原文用的是互补表述**：

| 条款 | 原文 | 语义 |
|---|---|---|
| 推荐意见11 | 直径**≤8 mm** | 含 8 |
| 推荐意见5 | 直径**>8 mm** | 不含 8 |

**因此 8.0 mm 唯一归属推荐意见11（或10），不归推荐意见5。**

**修正**：A 类采样已排除「下界恰等于相邻规则上界」的取值（第 29 轮引入的
半开区间逻辑），因此**不会生成归属不唯一的用例**。
本轮补充了 `INTERVAL_SEMANTICS` 常量，把四对互补关系的边界值显式记录下来：

| 互补对 | 边界值 |
|---|---|
| 推荐意见14 (≤8) / 推荐意见15 (>8) | 8.0 |
| 推荐意见12 (≤5) / 推荐意见13 (5~10) | 5.0 |
| 推荐意见11 (≤8, 有危险因素) / 推荐意见5 (>8) | 8.0 |
| 推荐意见10 (≤8, 无危险因素) / 推荐意见5 (>8) | 8.0 |

# 五、两项审计指控的处理记录

> **★ 后续轮次均已处理**（本节保留原始指控与修法说明，便于对照）：
> · 指控「评测对象是引擎而非系统」→ **已补端到端层**（`eval/agent_eval_runner.py`，58 条全量，走平台北向 API）
> · 指控「可溯源率恒真」→ **已改为只取引擎自然语言字段原文**；
>   并**如实披露**它与覆盖率**逐条一致**（引擎在 COVERED 分支的 `conclusion` 必写「适用【推荐意见N】」），**两者不作为独立证据**。

## 5.1 「评测对象是引擎而非系统」

**审计原文**：
> `eval/eval_runner.py:31-37` 直接 `import kg_mcp_server as kg`，
> 第 47 行调用 `kg.run_inference(q)`。
> **不经 MCP 协议、不经 Nexent 平台、不经 Skill 编排、不调用 LLM。**

**现状（v1.3 更新）**：✅ **已补上端到端层** —— 新增 `eval/agent_eval_runner.py` 走平台北向 API（完整 MCP + Skill + LLM 链路），58 条全量评测。引擎层（可解释误差归因）与端到端层**两层都报**。

**影响**：本评测衡量的是**引擎的条款判定能力**，
**不是**"智能体端到端的回答质量"。后者由 `端到端批量验证记录.md`
（8 场景，经完整 Agent 链路）单独覆盖。

**修法**：把评测改为调用 `POST /agent/run`，并**同时报两个数字**：
引擎层（可解释误差归因）+ 端到端层（真实能力）。**需实现 Agent 批量调用脚本。**

## 5.2 「可溯源率 100% 是恒真断言」

**审计原文**：
> `eval_runner.py:57` 取 `r.get("traceable")`，
> 而引擎在 `kg_mcp_server.py:784`（NOT_COVERED 分支）也返回 `"traceable": True`。
> 该指标**不可能不为 100%**。

**现状（v1.3 更新）**：✅ **已改** —— 改为只取引擎的**自然语言字段原文**（`conclusion` / `caveat` / `disclaimer`），不再由评测器拼装 `【】`。**⚠️ 但如实披露**：修正后该指标仍与覆盖率**逐条一致**（均为 54/58 = 93.1%）—— 这是引擎输出的**结构性事实**（COVERED 分支的 conclusion 必写「适用【推荐意见N】」），**因此两者不作为独立证据**。

**修法**：把该指标改为**真正解析回答文本**，统计"携带条款编号的回答占比"——
即使用修正后的 `CLAUSE_RE`。这样该指标才有波动、才有信息量。
